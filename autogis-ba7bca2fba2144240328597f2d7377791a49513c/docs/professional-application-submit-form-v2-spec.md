## 1. Цель

Уточнить структуру пользовательской заявки на активацию профессионального аккаунта до начала реализации.

Ключевые изменения этой ревизии:
- форма больше не опирается на один legacy-переключатель `businessType`;
- выбор деятельности строится по схеме `главный тип деятельности -> подтип деятельности`;
- после выбора главного типа обязательно открывается отдельный шаг уточнения подтипа;
- сценарий `частный исполнитель` отделяется от сценариев бизнеса через `activityGroupCode` и `activitySubtypeCode`;
- для бизнеса появляется обязательная ссылка на Яндекс.Карты;
- поля `contactPerson` и `email` исключаются из новой версии формы.

## 2. Контекст

Сейчас заявка отправляется через `POST /api/business-applications` и использует единый плоский набор полей для всех типов бизнеса.

В проекте уже введена каноническая иерархия деятельности:
- `activityGroupCode` — главный тип деятельности;
- `activitySubtypeCode` — уточняющий подтип.

Эта спецификация детализирует новую submit-форму и payload заявки. Она не заменяет архитектурную спецификацию модерации, а конкретизирует именно пользовательскую форму и состав данных, которые уходят на модерацию.

## 3. Модель выбора деятельности

### 3.1 Источник истины

Для новой формы источником истины являются:
- `activityGroupCode`;
- `activitySubtypeCode`.

Legacy-поле `businessType` допускается только как переходный compatibility-layer на backend. Новая форма не должна строить UX вокруг него.

### 3.2 Общий UX-поток выбора

1. Пользователь сначала выбирает главный тип деятельности.
2. После выбора главного типа форма обязана открыть отдельный шаг уточнения подтипа.
3. Подтип можно выбрать только из списка, относящегося к выбранному главному типу.
4. Пока подтип не выбран, заявка не считается заполненной по классификации деятельности.

Допустимый UX-контейнер для второго шага:
- modal dialog;
- bottom sheet;
- отдельный встроенный шаг формы.

Обязательное требование не в конкретном виде компонента, а в том, что уточнение подтипа должно происходить отдельно после выбора главного типа.

### 3.3 MVP-справочник главных типов и подтипов

#### `private_executor` — Частный исполнитель

Подтипы:
- `master` — `Автомастер`
- `washer` — `Автомойщик`

#### `auto_service` — Автосервис

Подтипы:
- `general_service` — `Автосервис`
- `tire_fitting` — `Шиномонтаж`
- `detailing` — `Детейлинг`

#### `auto_wash` — Автомойка

Подтипы:
- `classic` — `Классическая автомойка`
- `self_service` — `Самомойка`

### 3.4 Масштабируемость

Для MVP в форме фиксируются группы и подтипы, перечисленные выше.

При добавлении новых групп в справочник поведение формы должно оставаться тем же:
- сначала выбор главного типа;
- затем выбор подтипа только из допустимого списка группы;
- затем отображение релевантных полей заявки.

## 4. Сценарии заявителей

### 4.1 Частный исполнитель

Сценарий включается, если:
- `activityGroupCode = private_executor`

Особенности:
- поля `businessName` нет;
- вместо названия бизнеса используется имя исполнителя;
- имя берётся из профиля пользователя `user.name`;
- если `user.name` пустое, форма обязана запросить имя вручную перед отправкой заявки;
- поле `yandexMapsUrl` не показывается и не отправляется.

### 4.2 Бизнес

Сценарий включается, если:
- `activityGroupCode != private_executor`

Для MVP это:
- `auto_service`
- `auto_wash`

Особенности:
- сохраняется поле `businessName`;
- ссылка на Яндекс.Карты обязательна;
- `contactPerson` не используется;
- `email` не используется.

## 6. Правила UX

### 6.1 Общее поведение

1. Пользователь открывает форму активации профессионального аккаунта.
2. Форма загружает профиль пользователя через `/users/profile/me`.
3. Форма показывает шаг выбора главного типа деятельности.
4. После выбора главного типа открывается отдельное окно или шаг для выбора подтипа.
5. После выбора подтипа форма показывает только релевантные поля заявки.

### 6.2 Выбор главного типа и подтипа

1. До выбора главного типа поле подтипа неактивно.
2. После выбора главного типа подтип обязан быть выбран явно пользователем.
3. Если пользователь меняет главный тип:
   - выбранный ранее подтип сбрасывается;
   - очищаются ошибки валидации подтипа;
   - очищаются поля, которые не относятся к новому сценарию;
   - скрытые поля не попадают в payload.
4. UI должен показывать человекочитаемые названия главного типа и подтипа, но в payload отправлять коды.

### 6.3 Сценарий `private_executor`

1. Поле `businessName` скрыто.
2. Поле `yandexMapsUrl` скрыто.
3. Форма вычисляет `resolvedApplicantName = trim(user.name)`.
4. Если `resolvedApplicantName` непустое:
   - UI показывает это имя как значение из профиля;
   - отдельный обязательный ввод имени пользователю не нужен;
   - в payload всё равно уходит `applicantName = resolvedApplicantName`.
5. Если `resolvedApplicantName` пустое:
   - UI показывает обязательное поле `Имя`;
   - без заполнения этого поля заявка не отправляется.

Замечание:
- UI может показать имя из профиля как read-only поле или как информационный блок. Ключевое требование не в виде отображения, а в том, что значение должно быть автоматически взято из профиля и включено в отправляемый payload.

### 6.4 Сценарий бизнеса

1. Поле `businessName` обязательно.
2. Поле `yandexMapsUrl` обязательно.
3. Поля `contactPerson` и `email` отсутствуют.
4. Для ссылки на Яндекс.Карты рядом с полем нужна короткая подсказка:
   - пример смысла: "Добавьте ссылку на карточку или место в Яндекс.Картах, чтобы модератор мог подтвердить существование бизнеса".

## 7. Контракт данных

### 7.1 Нормализованный payload v2

Ниже указан канонический состав данных новой версии формы. В текущей кодовой базе это может временно передаваться как плоский JSON body. В целевой архитектуре модерации этот объект должен попадать в versioned `payload`.

#### Вариант для бизнеса

```json
{
  "activityGroupCode": "auto_service",
  "activitySubtypeCode": "tire_fitting",
  "businessName": "Шина 24",
  "city": "Москва",
  "address": "ул. Примерная, 10",
  "phone": "+79991234567",
  "yandexMapsUrl": "https://yandex.ru/maps/org/primer/1234567890",
  "comment": "Работаем по записи",
  "agreedToTerms": true
}
```

#### Вариант для частного исполнителя

```json
{
  "activityGroupCode": "private_executor",
  "activitySubtypeCode": "master",
  "applicantName": "Иван Петров",
  "city": "Москва",
  "address": "Москва",
  "phone": "+79991234567",
  "comment": "Выезжаю по району",
  "agreedToTerms": true
}
```

### 7.2 Правила валидации

1. `activityGroupCode` обязателен.
2. `activitySubtypeCode` обязателен.
3. `activitySubtypeCode` должен принадлежать выбранному `activityGroupCode`.
4. Если `activityGroupCode = private_executor`:
   - `applicantName` обязателен;
   - `businessName` не должен требоваться;
   - `yandexMapsUrl` не должен требоваться.
5. Если `activityGroupCode != private_executor`:
   - `businessName` обязателен;
   - `yandexMapsUrl` обязателен;
   - `applicantName` не должен требоваться.
6. `city` обязателен.
7. `phone` обязателен.
8. `address` остаётся опциональным.
9. `comment` остаётся опциональным.
10. `agreedToTerms` обязателен и должен быть `true`.
11. `contactPerson` и `email` не входят в новую клиентскую схему.

### 7.3 Валидация `yandexMapsUrl`

Минимальное правило MVP:
- поле должно содержать корректный URL;
- домен должен относиться к Яндекс.Картам или карточке организации в экосистеме Яндекса;
- финальное подтверждение корректности ссылки выполняет модератор вручную.

Слишком жёсткую URL-маску на MVP вводить не требуется, чтобы не ломать валидные варианты ссылок из мобильных и веб-версий Яндекс.Карт.

### 7.4 Источник списка групп и подтипов

Идеальный источник данных для формы:
- `GET /api/activity-groups`
- `GET /api/activity-groups/:groupCode/subtypes`

Для MVP допускается временный хардкод списка, если он совпадает с каноническим справочником и не расходится с backend-spec.

## 8. Что должен видеть модератор

### 8.1 Для бизнеса

В карточке заявки должны отображаться:
- главный тип деятельности;
- подтип деятельности;
- название бизнеса;
- город;
- адрес, если указан;
- телефон;
- ссылка на Яндекс.Карты как кликабельное поле;
- комментарий, если указан.

### 8.2 Для частного исполнителя

В карточке заявки должны отображаться:
- главный тип `Частный исполнитель`;
- выбранный подтип, например `Автомастер` или `Автомойщик`;
- имя исполнителя;
- город;
- адрес, если указан;
- телефон;
- комментарий, если указан.

## 9. Обратная совместимость

1. Исторические заявки со старыми полями `contactPerson` и `email` должны продолжать читаться в админке.
2. Исторические заявки, завязанные на legacy `businessType`, должны продолжать читаться в админке.
3. Новая форма не должна отправлять `contactPerson` и `email`.
4. Во время rollout backend должен корректно работать с двумя форматами:
   - legacy-данные в уже сохранённых заявках;
   - новая форма отправки v2 на `activityGroupCode + activitySubtypeCode`.
5. Новые правила обязательности должны применяться только к новым отправкам и повторным отправкам по v2.

## 10. Минимальные требования к реализации

1. Пользователь не может отправить заявку без выбора главного типа деятельности.
2. Пользователь не может отправить заявку без выбора подтипа деятельности.
3. После выбора главного типа обязательно открывается отдельный шаг или окно уточнения подтипа.
4. Для `activityGroupCode = private_executor` пользователь может отправить заявку без `businessName`, но не без `applicantName`.
5. Если `user.name` заполнено, имя для `private_executor` подставляется автоматически.
6. Если `user.name` пустое, форма требует ручной ввод имени.
7. Для любого бизнес-типа без `yandexMapsUrl` отправка невозможна.
8. Поля `contactPerson` и `email` отсутствуют и на UI, и в новом payload.
9. Скрытые поля не уходят в запрос.
10. Модератор видит ссылку на Яндекс.Карты только у бизнес-заявок.
11. При смене главного типа ранее выбранный подтип и зависимые поля сбрасываются.

## 11. Допущения этой ревизии

В этой версии спецификации зафиксированы следующие допущения:
- `phone` сохраняется в форме без изменений;
- `address` сохраняется в форме без изменений и остаётся опциональным;
- `agreedToTerms` сохраняется без изменений;
- источником имени частного исполнителя считается поле `user.name` из профиля пользователя;
- для MVP форма поддерживает группы `private_executor`, `auto_service`, `auto_wash`;
- если позже появятся новые группы, они обязаны работать по тому же паттерну `главный тип -> подтип`.

### 12.6 Тестирование

Обязательные сценарии проверки:
1. `private_executor/master` с именем из профиля отправляется без ручного ввода имени.
2. `private_executor/washer` при пустом `user.name` требует ручного ввода имени.
3. `auto_service/tire_fitting` не отправляется без `businessName`.
4. `auto_service/detailing` не отправляется без `yandexMapsUrl`.
5. `auto_wash/classic` и `auto_wash/self_service` корректно проходят через шаг выбора подтипа.
6. При смене главного типа старый подтип сбрасывается.
7. Повторная отправка после `needs_revision` использует новую структуру формы.
8. Историческая заявка legacy продолжает читаться в карточке модерации.
9. Список заявок модерации корректно фильтруется по `activityGroupCode` и `activitySubtypeCode`.

### 12.7 Что можно делать сразу, не дожидаясь полной модерационной миграции

Можно внедрять независимо:
1. Новую пользовательскую форму.
2. Новые поля и условную серверную валидацию на текущем endpoint.
3. Новое хранение `activityGroupCode/activitySubtypeCode` в текущей таблице.

Нельзя считать задачу полностью завершённой без:
1. schema `v2`;
2. корректного отображения новых полей в админке;
3. подтверждённой обратной совместимости для legacy-заявок.
