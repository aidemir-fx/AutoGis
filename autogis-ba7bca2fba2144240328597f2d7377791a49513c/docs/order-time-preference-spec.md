# Спецификация: предпочтение клиента по времени в заявке

## 1) Цель
Добавить в заявку отдельное поле, где клиент указывает, когда ему удобно обратиться, без выбора точного времени.
Точное время назначения заявки указывает мастер после принятия заявки.

## 2) Область изменений
- Форма создания заявки клиентом.
- Модель/контракт заявки (API + хранение).
- Карточка заявки в интерфейсе мастера.

Вне scope:
- логика назначения точного времени мастером;
- изменение статусов заявки;
- календарное планирование.

## 3) Бизнес-правило
1. Клиент при создании заявки выбирает предпочтение по времени.
2. Заявка сохраняется с этим предпочтением.
3. Мастер видит предпочтение в карточке заявки.
4. Точное время определяется и указывается мастером отдельным действием в существующем процессе.

## 4) Поле заявки
### 4.1 Новый атрибут
- `timePreference` (обязательное для новых клиентов)
- тип: enum/string

### 4.2 Допустимые значения
- `urgent` — «Срочно»
- `asap` — «Сразу»
- `tomorrow` — «На завтра»
- `during_day` — «В течение дня»
- `master_scheduled` — «Время назначит мастер»

## 5) UX-требования (клиент)
На форме «Оставить заявку» добавить отдельный блок:
- Заголовок/лейбл: «Когда вам удобно?»
- Тип поля: select/radio с вариантами из раздела 4.2
- Поле обязательно к заполнению
- Подсказка: «Точное время назначит мастер после принятия заявки»

Ошибки валидации:
- если не выбрано значение: «Выберите удобный вариант по времени»

## 6) UX-требования (мастер)
В карточке входящей заявки отображать:
- «Удобное время клиента: <значение>»

Отображается человекочитаемый лейбл (например, «На завтра»), а не технический код.

## 7) API-контракт
## 7.1 Создание заявки
`POST /orders`

Тело запроса (добавление):
- `timePreference: "urgent" | "asap" | "tomorrow" | "during_day" | "master_scheduled"`

## 7.2 Ответы с заявкой
Во всех ответах, где возвращается объект заявки (`/orders/*`, чат по заявке и т.д.), добавить поле:
- `timePreference`

## 7.3 Обратная совместимость
Если `timePreference` не передан (старый клиент), сервер:
- не падает;
- присваивает `master_scheduled` по умолчанию.

## 8) Валидация и ошибки
Серверная валидация:
- значение должно входить в enum из 4.2

Ошибка:
- HTTP 400
- code: `INVALID_TIME_PREFERENCE`
- message: `Invalid time preference`

## 9) Хранение данных
Таблица: `orders`

Добавить поле:
- `time_preference` (`varchar(32)` или DB enum)

Ограничения:
- допускается `NULL` только для legacy-записей до миграции;
- для новых записей значение должно быть заполнено (на уровне бизнес-логики).

## 10) Миграция
1. Добавить колонку `time_preference`.
2. Для существующих записей:
- либо оставить `NULL` и маппить в API на `master_scheduled`,
- либо выполнить backfill: `master_scheduled`.

Рекомендуемый вариант: backfill, чтобы убрать неоднозначность.

## 11) Нефункциональные требования
- Изменение не должно ломать текущие сценарии создания/чтения заявок.
- Добавление поля не должно менять существующие SLA по времени ответа API.

## 12) Критерии приёмки (QA)
1. Клиент не может отправить заявку без выбора `timePreference`.
2. При валидном значении заявка успешно создаётся.
3. Сохранённое значение возвращается в API чтения заявки.
4. Мастер видит выбранное клиентом предпочтение в карточке заявки.
5. Старый клиент (без поля) не ломается: заявка создаётся с `master_scheduled`.
6. При невалидном значении API возвращает 400 `INVALID_TIME_PREFERENCE`.

## 13) Примеры
Пример запроса:
```json
{
  "providerId": "uuid",
  "activityTypeId": "uuid",
  "description": "Шум в двигателе",
  "phone": "+7 900 000-00-00",
  "timePreference": "tomorrow"
}
```

Пример ответа:
```json
{
  "id": "uuid",
  "status": "pending",
  "description": "Шум в двигателе",
  "timePreference": "tomorrow",
  "createdAt": "2026-04-15T12:00:00Z"
}
```
