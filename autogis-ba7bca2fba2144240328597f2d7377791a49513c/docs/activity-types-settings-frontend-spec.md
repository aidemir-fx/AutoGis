# Спецификация: фронтенд настроек типов деятельности

## 1) Цель
Привести экраны настроек типов деятельности к единому качественному стандарту и устранить текущие баги в UI/UX:
- выравнивание блоков и полей;
- корректные названия секций/полей;
- добавление профильных полей для каждого типа деятельности;
- согласованность с API и валидацией.

В рамках этой спецификации используются два контура:
- Контур A (дизайн/UX/визуал, фронтенд-поведение): `auto_wash`, `auto_service`, `auto_shop`, `master`.
- Контур B (структура полей, данные, валидация бизнес-полей, API-контракты): `auto_wash`, `auto_service`, `auto_shop`.
- `master` (частный мастер) из контура B исключается.

---

## 2) Текущие выявленные проблемы (по коду)

### 2.1 Неверные подписи и тексты
- `AutoWashSettings`: поле адреса подписано как «Укажите автосервис на карте».
- `AutoShopSettings`: 
  - «Название автосервиса» вместо «Название автомагазина».
  - placeholder «Опишите услуги вашего автосервиса» вместо автомагазина.
  - поле карты подписано как автосервис.
- `AutoServiceSettings`: секция с графиком подписана «Статус» вместо «График работы».

### 2.2 Несогласованная структура секций
- В разных типах разные названия секций и порядок блоков.
- Из-за разной структуры контент визуально «прыгает», формы воспринимаются неровными.

### 2.3 Неиспользуемые профильные поля
- Для `auto_service` бэкенд уже поддерживает поля `hasParking`, `liftCount`, `warranty`, `hotline`, `brandSupport`, но форма их не редактирует.
- Для `auto_wash` и `auto_shop` нет профильных бизнес-полей, которые нужны для релевантного поиска и карточки.

---

## 3) Единый UX-стандарт для всех экранов (включая частного мастера)

## 3.1 Единый порядок секций
1. Статус
2. Основная информация
3. Профильные параметры типа деятельности
4. График работы
5. Дополнительные услуги (если применимо)
6. Кнопка сохранения

## 3.2 Сетка и выравнивание
- Desktop: 2 колонки (`grid-template-columns: 1fr 1fr`, `gap: 16`).
- Mobile (`< 900px`): 1 колонка.
- Все `Paper` одинаковые по отступам/радиусу/бордеру.
- Высота контролов одной строки унифицирована.
- Кнопка «Карта» всегда в одном ряду с полем адреса.

## 3.3 Единые состояния
- `loading`: скелетон/заглушка с понятным текстом.
- `error`: текст + кнопка «Повторить».
- `empty profile`: понятное сообщение.
- `saving`: disabled + loading на кнопке.

## 3.4 Применимость к `master`
- Все требования раздела 3 применяются к экрану настроек частного мастера.
- Раздел 3 не добавляет и не изменяет структуру полей `master`; только визуальные и UX-правила.

## 4) Матрица полей по типам (без частного мастера)

## 4.1 Общие поля (оставить для всех 3 типов)
- `fullName` — название
- `workingPhone` — рабочий телефон
- `address` + `coordinates` — адрес и точка на карте
- `description` — описание
- `workingDays`, `workFrom`, `workTo` — график
- `status` — статус доступности

Правило: все подписи и helper-тексты должны содержать правильный тип бизнеса (автомойка/автосервис/автомагазин).

## 4.2 `auto_wash` (автомойка)

### Оставить
- Текущие общие поля
- `additionalServices`

### Добавить
- `washType` (enum):
  - `self_service` — Самомойка
  - `classic` — Классическая автомойка
- `boxCount` (int, >=1) — Количество боксов
- `washerCount` (int, >=0) — Количество мойщиков
- `hasWaitingArea` (bool) — Зона ожидания
- `payments` (string[]) — Способы оплаты (`cash`, `card`, `sbp`)

### Переименовать тексты
- «Информация о сервисе» -> «Информация об автомойке»
- «Укажите автосервис на карте» -> «Укажите автомойку на карте»

## 4.3 `auto_service` (автосервис)

### Оставить
- Общие поля
- `professions`

### Добавить/включить в UI (уже есть на бэкенде)
- `hasParking` (bool) — Есть парковка
- `liftCount` (int, >=0) — Количество подъемников
- `warranty` (bool) — Гарантия на работы
- `hotline` (string, optional) — Горячая линия
- `brandSupport` (string[]) — Поддерживаемые марки

### Переименовать тексты
- Секция с временем: «Статус» -> «График работы»
- Placeholder названия: убрать лишний пробел, сделать «Введите название автосервиса»

## 4.4 `auto_shop` (автомагазин)

### Оставить
- Общие поля
- `additionalServices` (если используете как список доп. опций)

### Добавить
- `shopType` (enum):
  - `parts_store` — Магазин запчастей
  - `mixed` — Смешанный ассортимент
  - `specialized` — Специализированный
- `hasPickup` (bool) — Самовывоз
- `deliveryAvailable` (bool) — Доставка
- `deliveryRadiusKm` (int, >=0, показывать только если `deliveryAvailable=true`)
- `brands` (string[]) — Бренды в наличии
- `productCategories` (string[]) — Категории товаров

### Переименовать тексты
- «Информация о сервисе» -> «Информация об автомагазине»
- «Название автосервиса» -> «Название автомагазина»
- «Опишите услуги вашего автосервиса» -> «Опишите товары и услуги автомагазина»
- «Укажите автосервис на карте» -> «Укажите автомагазин на карте»

## 5) Валидация (frontend, без частного мастера)

## 5.1 Общие правила
- `fullName`: обязательное, 2..120 символов
- `workingPhone`: обязательное, маска +7, минимум 11 цифр
- `address`: обязательное
- `coordinates`: обязательные, нельзя сохранять `(0,0)`
- `description`: до 1000 символов
- `workingDays`: минимум 1 выбранный день
- `workFrom/workTo`: обязательные, `workFrom < workTo`

## 5.2 Специфичные правила
- `boxCount`, `washerCount`, `liftCount`, `deliveryRadiusKm`: только целые >= 0
- условные поля отображаются и валидируются только при включенном флаге:
  - `deliveryRadiusKm` только если `deliveryAvailable=true`

## 6) API-контракт (что нужно на бэкенде, без частного мастера)

## 6.1 Уже поддерживается (нужно вывести в UI)
- `auto_service`:
  - `hasParking`, `liftCount`, `warranty`, `hotline`, `brandSupport`

## 6.2 Требует расширения DTO/Entity/миграций
- `auto_wash`:
  - `washType`, `boxCount`, `washerCount`, `hasWaitingArea`, `payments`
- `auto_shop`:
  - `shopType`, `hasPickup`, `deliveryAvailable`, `deliveryRadiusKm`, `brands`, `productCategories`

Рекомендуемый подход:
- добавить поля в `entities.go`;
- добавить в `UpdateAutoWashRequest`, `AutoWashResponse`, `UpdateAutoShopRequest`, `AutoShopResponse`;
- обновить маппинг usecase/handler;
- добавить миграцию с дефолтами и nullable там, где нужно.

---

## 7) Технические требования к фронту

- Использовать единый переиспользуемый компонент секции настроек (обертка `Paper` + `Title` + grid), чтобы исключить расхождения верстки.
- Вынести конфигурацию полей в типизированную схему по activity type (конфиг-ориентированный рендер).
- Привести все подписи/плейсхолдеры к словарю i18n/константам, чтобы не допускать копипаст-ошибок.
- Для новых enum-полей использовать `Select` с человекочитаемыми label.
- Для массивов (`brands`, `productCategories`, `brandSupport`) использовать `TagSelector`.

Примечание по области действия:
- Визуальные требования этого раздела применяются к `master`.
- Требования этого раздела по конфигурации бизнес-полей относятся только к `auto_wash`, `auto_service`, `auto_shop`.

---

## 8) Критерии приемки (QA)

1. UX/визуал: на каждом экране (`автомойка`, `автосервис`, `автомагазин`, `частный мастер`) единая сетка, отступы, состояния и визуальная консистентность.
2. UX/визуал: на экранах нет чужих названий типа бизнеса в заголовках/подписях/placeholder.
3. Данные/поля (только `автомойка`, `автосервис`, `автомагазин`): нельзя сохранить форму без валидных координат и обязательных полей.
4. Для `auto_service` можно читать/редактировать `hasParking`, `liftCount`, `warranty`, `hotline`, `brandSupport`.
5. Для `auto_wash` и `auto_shop` работают новые профильные поля (после расширения API).
6. Для `auto_wash`, `auto_service`, `auto_shop` после сохранения данные корректно переоткрываются и отображаются без потерь.
7. Ошибки API показываются понятным текстом на всех соответствующих экранах.
