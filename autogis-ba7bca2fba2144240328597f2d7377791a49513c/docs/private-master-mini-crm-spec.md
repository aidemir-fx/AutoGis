# Спецификация: mini-CRM для частного мастера

## 1. Цель
Создать мини-CRM в профессиональном кабинете частного мастера для управления заявками и расписанием записей клиентов.

## 2. Область решения
Система покрывает:
- просмотр и обработку входящих заявок;
- категоризацию заявок по статусам;
- подтверждение/отмену заявок с указанием причины отмены;
- переход в чат с клиентом из карточки заявки;
- календарь и расписание подтвержденных записей;
- быстрый обзор актуальных заявок на главном экране профкабинета.

Ограничение источника данных:
- для превью и детальной карточки использовать только данные, приходящие из текущей формы заявки и/или стандартные служебные поля заявки (`id`, `status`, `createdAt` и т.д.);
- не закладывать поля, которых нет в форме и текущем контракте.

## 3. Роли
- Частный мастер (основной пользователь).

## 4. Бизнес-термины
- `Заявка` — обращение клиента на запись к мастеру.
- `Актуальные заявки` — новые/важные заявки, требующие внимания мастера в ближайшее время.
- `Подтвержденная запись` — заявка со согласованным временем визита.
- `Чат по заявке` — чат между клиентом и мастером, автоматически создаваемый при создании заявки.

## 5. Статусы заявок
Канонические backend-статусы (источник истины):
1. `pending`
2. `scheduled`
3. `completed`
4. `cancelled`

UI-лейблы:
- `pending` -> `Ожидает подтверждения`
- `scheduled` -> `В процессе` (включая подтвержденные и запланированные записи)
- `completed` -> `Выполнена`
- `cancelled` -> `Отменена`

Разрешенные переходы:
- `pending` -> `scheduled` (мастер подтверждает и назначает `confirmedDateTime`)
- `pending` -> `cancelled` (мастер отменяет с обязательным `cancelReason`)
- `scheduled` -> `completed` (работа завершена)
- `scheduled` -> `cancelled` (отмена после подтверждения с обязательным `cancelReason`)

Недопустимые переходы:
- Любой переход из `completed` или `cancelled` в другие статусы.

## 6. Основные экраны и сценарии

### 6.1 Главный экран профессионального кабинета
Содержит два блока:
1. `Актуальные заявки` (ограниченный список, например 3-5 шт.).
2. `Расписание` (ближайшие подтвержденные записи из календаря).

Требования:
- Каждая заявка в блоке актуальных отображается в виде компактной превью-карточки.
- Есть кнопка `Все заявки`, ведущая в полный список.
- Расписание под актуальными заявками показывает: клиент, дата, время, длительность/окно записи, статус (подтверждена).

### 6.2 Полный список заявок
Требования:
- Список заявок с сортировкой (по умолчанию: сначала ближайшие/новые).
- Фильтрация по статусам:
  - `Ожидает подтверждения`
  - `В процессе`
  - `Выполнена`
  - `Отменена`
- Каждая строка/карточка имеет превью основной информации.

Минимум данных в превью:
- ID или номер заявки;
- имя клиента (если нет — телефон клиента);
- марка автомобиля (`carBrand`, если доступно в контракте);
- краткое описание проблемы (первые 1-2 строки `description`);
- предпочтение по времени (`timePreference`: срочно/не срочно/иные поддерживаемые значения);
- текущий статус;
- дата создания.

### 6.3 Детальная карточка заявки
Открывается по нажатию на превью в списке.

Содержимое:
- имя клиента (`name`, если доступно) и телефон (`phone`);
- марка автомобиля (`carBrand`, если доступно);
- полное описание проблемы (`description`);
- предпочтение по времени (`timePreference`);
- фото по заявке (если прикреплены);
- история изменения статуса (опционально, но рекомендуется);
- действия мастера.

Действия мастера на экране заявки:
1. `Перейти в чат с клиентом`.
2. `Подтвердить заявку`:
   - выбрать/указать точное время записи;
   - сохранить подтверждение;
   - отразить запись в календаре.
3. `Отменить заявку`:
   - обязательно заполнить поле `Причина отмены`;
   - сохранить отмену;
   - изменить статус на `Отменена`.

### 6.4 Экран календаря
Требования:
- Отображает подтвержденные записи мастера.
- Для каждой записи показываются:
  - клиент;
  - дата и время;
  - услуга/краткое описание;
  - связь с исходной заявкой.
- Доступны режимы просмотра: минимум `день` и `неделя` (опционально `месяц`).
- По клику на запись должен быть переход в соответствующую детальную карточку заявки.
- Длительность слота берется из:
  - `activityType.durationMinutes`, если доступно;
  - иначе дефолт `60` минут (MVP-правило).
- В календаре не допускаются пересечения подтвержденных записей одного мастера:
  - при конфликте backend возвращает `409 Conflict`;
  - подтверждение/перенос не сохраняется до выбора свободного времени.

## 7. Логика обработки заявок

### 7.1 Подтверждение заявки
1. Мастер открывает заявку.
2. Указывает время записи.
3. Подтверждает.
4. Система:
   - меняет статус заявки `pending -> scheduled`;
   - создает событие в календаре;
   - отображает запись в блоке расписания на главном экране.

### 7.2 Отмена заявки
1. Мастер нажимает `Отменить`.
2. Заполняет обязательное поле `Причина отмены`.
3. Подтверждает отмену.
4. Система:
   - переводит заявку в `Отменена`;
   - сохраняет причину отмены;
   - убирает/не добавляет запись в подтвержденное расписание.

Валидация:
- Если поле причины пустое, отмена невозможна.

### 7.3 Правила календаря и конкурентного доступа
1. Все операции подтверждения/переноса времени выполняются атомарно на backend.
2. При конкурентном изменении заявки применяется optimistic concurrency (`updatedAt`/версия):
   - если заявка уже изменена другим действием, backend возвращает `409 Conflict`;
   - фронт обязан перечитать карточку и показать актуальный статус.
3. Backend проверяет пересечения по `providerId + confirmedDateTime + duration` до сохранения `scheduled`.
4. Время хранится в UTC, отображается в часовом поясе мастера.

### 7.4 Чат по заявке (обязательное поведение)
1. Сразу после создания заявки клиентом чат с мастером запускается автоматически.
2. После отправки заявки клиент автоматически попадает в этот чат и ожидает ответа мастера.
3. Любая обратная связь мастера по заявке дублируется в чат системным сообщением:
   - подтверждение заявки;
   - отклонение/отмена заявки;
   - иные статусные изменения по заявке.
4. Кнопка `Перейти в чат` у мастера не должна блокироваться:
   - в штатном сценарии чат уже существует;
   - для legacy-данных без `chatId` backend делает ленивое auto-create и сразу открывает чат.

## 8. Функциональные требования (MVP)
1. Вход в профессиональный кабинет с доступом к блоку заявок и календарю.
2. Вывод актуальных заявок на главном экране (ограниченное количество).
3. Переход из главного экрана в полный список заявок.
4. Фильтрация и сортировка заявок в полном списке.
5. Превью-карточки заявок с основной информацией.
6. Детальная карточка заявки.
7. Действие `Перейти в чат` из карточки заявки.
8. Подтверждение заявки с указанием времени.
9. Отмена заявки с обязательным полем причины.
10. Календарь подтвержденных записей.
11. Отображение ближайшего расписания на главном экране.

## 9. Нефункциональные требования
- Интерфейс адаптивный (desktop + mobile).
- Обновление статусов и календаря без потери данных при перезагрузке.
- Время хранится и отображается в едином часовом поясе мастера.
- Поле причины отмены логируется и доступно для просмотра в карточке заявки.
- Все операции с заявками доступны только владельцу заявки (`providerId` текущего мастера).
- Для чужих заявок backend возвращает `403` (или `404`, если принята политика скрытия существования).
- Все изменения статуса пишутся в аудит-лог: `orderId`, `oldStatus`, `newStatus`, `actorId`, `timestamp`.

## 10. Данные и поля сущности "Заявка" (минимум)
- `id`
- `providerId`
- `customerId`
- `activityTypeId`
- `name` (из формы, если поддержано backend-контрактом)
- `phone`
- `carBrand` (из формы, если поддержано backend-контрактом)
- `description`
- `timePreference`
- `photoAssetIds` (опционально, если поддержано backend-контрактом)
- `customer` (`name`, `phone`)
- `provider` (`name`, `phone`)
- `activityType` (`id`, `name`, `displayName`)
- `status` (`pending`, `scheduled`, `completed`, `cancelled`)
- `createdAt`
- `confirmedDateTime` (nullable)
- `cancelReason` (nullable, mandatory when canceled)
- `chatId` (обязателен для новых заявок; nullable только для legacy до миграции)
- `updatedAt`

### 10.1 Фактическая доступность в текущем backend (на момент спецификации)
По текущему контракту `POST /orders` и `OrderResponse` гарантированно доступны:
- `id`, `providerId`, `customerId`, `activityTypeId`;
- `description`, `timePreference`, `phone`, `status`, `createdAt`, `updatedAt`;
- вложенные объекты `customer`, `provider`, `activityType`.

Поля формы, требующие отдельной поддержки в backend-контракте (если ещё не добавлены):
- `name`;
- `carBrand`;
- `photoAssetIds`;
- `cancelReason`;
- `confirmedDateTime`.

## 11. Критерии приемки
1. После входа в профессиональный кабинет мастер видит:
   - несколько актуальных заявок;
   - ниже блок расписания подтвержденных записей.
2. По кнопке `Все заявки` открывается полный список с фильтрами по 4 статусам.
3. Каждая заявка в списке имеет превью основной информации.
4. По клику открывается детальная карточка заявки.
5. Из карточки можно:
   - перейти в чат клиента;
   - указать время и подтвердить заявку;
   - отменить заявку.
6. При отмене без причины система не позволяет сохранить действие.
7. После подтверждения заявка отражается в календаре и в блоке расписания.
8. Отмененная заявка отображается в категории `Отменена` с сохраненной причиной.

## 12. Рекомендации по развитию (post-MVP)
- Напоминания мастеру о ближайших записях.
- Автоуведомления клиенту при подтверждении/отмене.
- Поиск по заявкам.
- Теги/приоритеты заявок.

## 13. GAP-лист для backend (обязательные доработки под эту спецификацию)

### 13.1 Цель GAP-листа
Закрыть расхождения между текущей формой заявки на фронте и фактическим backend-контрактом, чтобы:
- превью заявки;
- детальная карточка заявки;
- календарь подтвержденных записей;
- отмена с причиной
работали на реальных данных без условных заглушек.

### 13.2 Что уже покрыто backend
По текущему контракту заявки уже поддерживаются:
- создание и чтение заявки (`POST /orders`, `GET /orders/*`);
- поля: `id`, `providerId`, `customerId`, `activityTypeId`, `description`, `timePreference`, `phone`, `status`, `createdAt`, `updatedAt`;
- статусы: `pending`, `scheduled`, `completed`, `cancelled`;
- вложенные данные: `customer`, `provider`, `activityType`;
- обновление статуса (`PUT /orders/:id/status`).

### 13.3 Что не хватает (GAP)
1. Поле `name` из формы не сохраняется и не возвращается в объекте заявки.
2. Поле `carBrand` из формы не сохраняется и не возвращается в объекте заявки.
3. Поле `photoAssetIds` из формы не сохраняется и не возвращается в объекте заявки.
4. Для отмены заявки отсутствует хранение `cancelReason` и обязательная валидация причины при переходе в `cancelled`.
5. Для подтверждения/расписания отсутствует дата-время назначения мастером (`confirmedDateTime`), нужная для календаря.
6. Текущее перечисление `timePreference` в backend расходится с UI-вариантами формы (`urgent`, `not_urgent`), требуется унификация.
7. Не зафиксированы разрешенные переходы статусов и проверки конкурентных обновлений.
8. Не описаны обязательные проверки ownership (доступ мастера только к своим заявкам).
9. Не зафиксировано обязательное создание чата при создании заявки и auto-create fallback для legacy.

### 13.4 Требуемые изменения по контракту API
1. Расширить `CreateOrderRequest`:
   - добавить `name: string` (required);
   - добавить `carBrand: string` (required);
   - добавить `photoAssetIds: string[]` (optional).
2. Расширить `OrderResponse`:
   - добавить `name`;
   - добавить `carBrand`;
   - добавить `photoAssetIds`;
   - добавить `confirmedDateTime` (nullable);
   - добавить `cancelReason` (nullable).
3. Расширить `UpdateOrderStatusRequest`:
   - добавить `confirmedDateTime` (required при переводе в `scheduled`, если бизнес-процессом требуется назначение времени);
   - добавить `cancelReason` (required при переводе в `cancelled`).
4. Унифицировать `timePreference`:
   - либо backend принимает и возвращает строго `urgent|not_urgent`;
   - либо фронт и backend совместно переходят на единый enum (без смешивания форматов).
5. Добавить контрактные гарантии по статусам:
   - backend валидирует только разрешенные переходы (`pending->scheduled|cancelled`, `scheduled->completed|cancelled`);
   - при недопустимом переходе возвращает `422`.
6. Добавить ownership-проверки во все endpoints чтения/изменения заявок:
   - доступ только при совпадении `providerId` и текущего пользователя.
7. Добавить контракт по чату:
   - при создании заявки возвращать `chatId`;
   - если у legacy-заявки `chatId` отсутствует, `GET /orders/:id/chat` (или эквивалент) должен создавать чат и возвращать его без ошибки.

### 13.5 Требуемые изменения модели данных (БД/Entity)
1. Добавить в сущность `orders`:
   - `name` (varchar, not null);
   - `car_brand` (varchar, not null);
   - `photo_asset_ids` (jsonb/text[]/связь с media table);
   - `confirmed_date_time` (timestamp with time zone, nullable);
   - `cancel_reason` (text, nullable).
2. Для чатов:
   - обеспечить связь `orders.chat_id` с таблицей чатов;
   - для новых заявок `chat_id` должен заполняться при создании.
3. Добавить миграцию для существующих данных:
   - безопасные default-значения/nullable-этап;
   - последующее ужесточение not null (где применимо) после обратной совместимости.

### 13.6 Бизнес-валидации на backend
1. Запретить создание заявки без `name`, `phone`, `carBrand`, `description`, `timePreference`.
2. При `status -> scheduled` валидировать `confirmedDateTime` (если используется календарный сценарий подтверждения).
3. При `status -> cancelled` валидировать непустой `cancelReason`.
4. Валидация `photoAssetIds`:
   - принадлежность файлов пользователю;
   - допустимость ссылок/asset-id;
   - лимиты количества (до 10) и типов на уровне бизнес-правил.
5. При подтверждении/переносе валидировать отсутствие пересечений в календаре мастера.
6. При любом чтении/изменении заявки валидировать ownership по `providerId`.
7. При создании заявки гарантировать создание `chatId`; при отсутствии у legacy выполнять auto-create.

### 13.7 Обратная совместимость и порядок внедрения
1. Сначала расширить backend-контракт и хранение (с nullable/optional режимом).
2. Затем включить выдачу новых полей в ответах (`GET /orders/*`).
3. После выката фронта включить строгую обязательность новых полей на backend.
4. Для старых заявок без новых полей:
   - корректно отдавать `null`/пустые значения;
   - UI должен показывать fallback (например, если `name` пусто, показывать `phone`).
5. Для legacy-заявок без `chatId`:
   - при первом переходе в чат создавать его автоматически;
   - после создания сохранять `chatId` в `orders`.

### 13.8 Критерии закрытия GAP-листа
1. Заявка, созданная из текущей формы, возвращается из API со всеми полями формы (`name`, `phone`, `carBrand`, `timePreference`, `description`, `photoAssetIds`) и служебными полями.
2. При отмене заявки без `cancelReason` backend возвращает ошибку валидации.
3. При успешной отмене `cancelReason` сохраняется и приходит в `GET /orders/*`.
4. При подтверждении заявки время (`confirmedDateTime`) сохраняется и используется в календарной выдаче.
5. Enum `timePreference` одинаково трактуется фронтом и backend без преобразований, ломающих данные.
6. Нельзя подтвердить/перенести запись в занятый слот того же мастера (возвращается `409`).
7. Доступ к заявке невозможен для другого мастера (ownership enforced).
8. У новой заявки после создания всегда есть `chatId`, а переход `Перейти в чат` не блокируется.
9. Подтверждение/отмена/обратная связь мастера по заявке дублируются в чат системными сообщениями.
